# 情境檢核清單

依使用者帶來的內容挑選對應段落；不必每一題都寫進輸出，只挑出「有問題」或「沒交代」的項目。

## 目錄
A. 向上報告／簡報
B. 簽呈、提案、系統或 AI 需求、預算採購
C. KPI 加分申請或審查
D. 教育訓練、人才培育
E. 跨單位分工、權責協調
F. 執行計畫、進度回報、列管
G. 單純決策提問

---

## A. 向上報告／簡報
- [ ] 決策者是誰？他現在最在意的是成本、風險、時效還是效益？正在挑戰什麼經營問題？
- [ ] 時間有多長？短時間報告不能塞幾十頁＋Demo；開場先給全貌（藍圖／一句話結論）。
- [ ] 是否結論先行？讓決策者一眼知道：目前階段、目的、要決定什麼、下一步。
- [ ] 是否把分散的技術項目包裝成管理主題，而不是列系統清單、堆功能？
- [ ] 有沒有不必要的技術名詞？若沒有清楚使用情境，改成白話效益。
- [ ] 是否分清已完成成果（PoC）與未來規劃？規劃不可寫成承諾或已核定範圍。
- [ ] 長期願景是否「淡淡帶過」，沒有喧賓奪主？
- [ ] 若對方正質疑成本，是否避免先丟高額系統預算，改提具體可行的管理改善＋經濟方案？
- [ ] 是否有一頁式圖卡或小抄，而不只附正式簽案？

## B. 簽呈、提案、系統或 AI 需求、預算採購
- [ ] 需求與價值：誰提出、為何需要、主要使用者與關係人、預期改善？
- [ ] 業務規則、資料定義、流程是否已由主辦業務單位整合共識？還是想讓資訊單位先開發再說？
- [ ] 是否先分類情境、釐清 SOP 與制度，再定技術？複雜例外是否可用 SOP 處理而非硬寫程式？
- [ ] 有沒有低成本、可驗證的小題先做（POC → 少數驗證 → 推廣）？
- [ ] 替代方案：自建、委外、既有產品、既有平台、雲／地／混合、業務自主小工具？
- [ ] 量化比較：建置、維運、人力、資料儲存、備份、資安、AI 推論邊際成本、時程、效益、風險。
- [ ] 數據口徑：實際值／估算／假設是否分開？分母是否正確？
- [ ] 是否做了減法？每個功能都解決核心痛點嗎？是否分出核心功能與後續擴充？
- [ ] 權責：IT 與 OT、資訊單位與業務單位、總部與據點的責任是否寫清？
- [ ] 預判質疑：高層、會計、業務、維運單位會問什麼？擬答與佐證是否備妥？
- [ ] 自己的建議：建議方案、待主管決策之處、下次回報成果與時間？
- [ ] 預算排序：必要／已執行項目優先；可否分年、減量、先單點驗證？（排後≠否定）
- [ ] 法規、採購規範、資安經費等，是否已查核？未查核就標待確認。

## C. KPI 加分申請或審查
先分類：

| 類型 | 資訊單位基本態度 | 須說明 |
|---|---|---|
| 自主應用 AI／資訊工具，有明確痛點與完成成果 | 原則建議加分 | 自主作為、驗證方式、前後量化效益 |
| 正式系統建置或精進 | 先協調；有跨單位效益與創新價值才主動支持 | 目的、與資訊單位溝通分工、兩單位以上受益、量化效益 |
| 原有職掌的單位內系統／例行改善 | 原則不表示加分意見（≠反對） | 由提案單位向 KPI 權責單位自行說明 |
| 需求或成果不清、只有泛稱或研究報告 | 請補述或暫不建議 | 問題、範圍、交付成果、驗證方法、可量化改善 |

每案最少回答四題：
- [ ] **為什麼做？** 主要使用者、關係人、原始痛點。
- [ ] **誰完成？** 自主使用或開發了哪些工具？哪些由資訊單位／委外負責？
- [ ] **怎麼驗證？** 成品、試用、測試題、樣本、驗收方法。
- [ ] **改善多少？** 基準值與導入後數值（工時、成本、錯誤率、筆數）、受益單位數、計算口徑。
- [ ] RAG／問答類：標準題、來源核對、正確率／符合度、無答案辨識；門檻依應用風險訂，不套固定數字。
- [ ] 措辭：「無法判斷／不表示加分意見」與「反對」是否分清？最終評核權是否留給 KPI 權責單位？

## D. 教育訓練、人才培育
- [ ] 目的：是要讓學員立刻精通，還是建立「知道有什麼」的腦中索引與拆題能力？
- [ ] 學員是誰？基礎差異？課後希望帶走什麼（「原來也可以這樣做」）？
- [ ] 教材是否從需求剖析 → 元件認識 → 迭代版本 → 實際業務場景 → 部署分享，涵蓋完整歷程？
- [ ] 主辦權責：全組織訓練由人資主責，資訊單位提供專業與必要課程？分工與預算是否依最新資訊？
- [ ] 量化比較：各單位課程總額、堂數、時數、每堂單價、內容規格；分母是否正確；內部講師／助教的人力成本是否計入？
- [ ] 是否考慮外部專家承擔規劃與授課，資訊單位保留專業把關？
- [ ] 報價項目是否界定必要服務與可驗收成果？
- [ ] 成效：課後如何檢驗學員能獨立拆解實際問題？

## E. 跨單位分工、權責協調
- [ ] 這件事的權責主體是誰？資訊單位是陪跑還是攬責？
- [ ] 業務單位是否親自參與拆題、決定 SOP、欄位、KPI、行動計畫？是否有具協調／決策能力的主管在場？
- [ ] 建議是否只給方法、架構與一個小題示範，而不是替對方寫完整企劃？
- [ ] 是否有替其他單位「創設規則」的情況？跨單位定義不一致處是否先形成共識？
- [ ] 協助範圍：基礎設施、資安、技術整合、資料標準——這些要積極協作。
- [ ] 是否回溯原始往來紀錄，確認當初分工的表述？
- [ ] 溝通前是否整理：要談的問題、關係人、所需佐證、可能質疑與擬答？

## F. 執行計畫、進度回報、列管
- [ ] 全貌：數量、對象、類型、時程、先後次序、驗收條件。
- [ ] 日期：預定目標日與最晚驗收日是否分開？是否誤寫成已完成？
- [ ] 使用者便利：是否替使用者（尤其長官）減少額外手續？跨單位資源是否整合？
- [ ] 資料規範：表格狀態與欄位定義是否跨人可讀、一致？有沒有列未採購的服務造成誤會？
- [ ] 回報：短摘要包含 目標與數量／已完成與剩餘／下一步與日期／障礙與需協調事項／預計驗收日，並附詳表連結？
- [ ] 是否主動回報，讓主管不必追問？
- [ ] 是否有後續知識累積（做完的經驗寫下來可傳承）？

## G. 單純決策提問
1. 先用一句話重述目的與要解決的問題。
2. 分辨眼前必交付 vs 中長期工作，與時間限制。
3. 給出熊主管的判斷方向與理由，附類似案例或原則對照。
4. 區分：技術可行、業務可用、組織可落實。
5. 提出可立即採取的下一步、待驗證假設、留給使用者自己想的部分。
