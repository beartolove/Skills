# 情境檢核清單

依使用者帶來的內容挑選對應段落；不必每一題都寫進輸出，只挑出「有問題」或「沒交代」的項目。

## 目錄
A. 向上報告／簡報
B. 簽呈、提案、系統或 AI 需求、預算採購
C. KPI 加分申請或審查
D. 教育訓練、人才培育
E. 跨單位分工、權責協調
F. 執行計畫、進度回報、列管
G. 單純決策提問
H. 採購評選（評選委員角度）
I. 高影響管控措施推動（資安、權限、白名單）
J. 研究報告、效益估算、政策分析
K. 共享平台／AI 服務營運與資源治理
L. 競賽、請益會議、多輪審閱的交版節奏

## A. 向上報告／簡報
- [ ] 決策者是誰？他現在最在意的是成本、風險、時效還是效益？正在挑戰什麼經營問題？
- [ ] 時間有多長？短時間報告不能塞幾十頁＋Demo；開場先給全貌（藍圖／一句話結論）。
- [ ] 是否結論先行？讓決策者一眼知道：目前階段、目的、要決定什麼、下一步。
- [ ] 是否把分散的技術項目包裝成管理主題，而不是列系統清單、堆功能？
- [ ] 有沒有不必要的技術名詞？若沒有清楚使用情境，改成白話效益。
- [ ] 是否分清已完成成果（PoC）與未來規劃？規劃不可寫成承諾或已核定範圍。
- [ ] 長期願景是否「淡淡帶過」，沒有喧賓奪主？
- [ ] 若對方正質疑成本，是否避免先丟高額系統預算，改提具體可行的管理改善＋經濟方案？
- [ ] 是否有一頁式圖卡或小抄，而不只附正式簽案？
- [ ] 這次會議的階段目的是什麼？請益會只需可討論的初稿，不必一次做盡（見 L）。

## B. 簽呈、提案、系統或 AI 需求、預算採購
- [ ] 需求與價值：誰提出、為何需要、主要使用者與關係人、預期改善？
- [ ] 業務規則、資料定義、流程是否已由主辦業務單位整合共識？還是想讓資訊單位先開發再說？
- [ ] 是否先分類情境、釐清 SOP 與制度，再定技術？複雜例外是否可用 SOP 處理而非硬寫程式？
- [ ] 有沒有低成本、可驗證的小題先做（POC → 少數驗證 → 推廣）？
- [ ] 替代方案：自建、委外、既有產品、既有平台、雲／地／混合、業務自主小工具？
- [ ] 量化比較：建置、維運、人力、資料儲存、備份、資安、AI 推論邊際成本、時程、效益、風險。
- [ ] 數據口徑：實際值／估算／假設是否分開？分母是否正確？
- [ ] 是否做了減法？每個功能都解決核心痛點嗎？是否分出核心功能與後續擴充？
- [ ] 權責：IT 與 OT、資訊單位與業務單位、總部與據點的責任是否寫清？
- [ ] 預判質疑：高層、會計、業務、維運單位會問什麼？擬答與佐證是否備妥？
- [ ] 自己的建議：建議方案、待主管決策之處、下次回報成果與時間？
- [ ] 預算排序：必要／已執行項目優先；可否分年、減量、先單點驗證？（排後≠否定）
- [ ] 法規、採購規範、資安經費等，是否已查核？未查核就標待確認。
- [ ] 總成本（TCO）：是否用符合 SOP 的單位（每張／每批）比較，並納入 Token、平台、維運、業務人工覆核、重工？品質等級是否與業務共同取捨？
- [ ] 外部補助、產學合作、採購是否各自獨立論證？有沒有把兩個不同性質的案子串在一起，造成稽核疑慮？
- [ ] 市場調查（三家可比較方案）是否與法定採購程序分開？是否誤把金額門檻當成可指定廠商的理由？
- [ ] 外部顧問／PMO 的角色是補專業，還是被期待代替公司做決策？

## C. KPI 加分申請或審查
先分類：

| 類型 | 資訊單位基本態度 | 須說明 |
|---|---|---|
| 自主應用 AI／資訊工具，有明確痛點與完成成果 | 原則建議加分 | 自主作為、驗證方式、前後量化效益 |
| 正式系統建置或精進 | 先協調；有跨單位效益與創新價值才主動支持 | 目的、與資訊單位溝通分工、兩單位以上受益、量化效益 |
| 原有職掌的單位內系統／例行改善 | 原則不表示加分意見（≠反對） | 由提案單位向 KPI 權責單位自行說明 |
| 需求或成果不清、只有泛稱或研究報告 | 請補述或暫不建議 | 問題、範圍、交付成果、驗證方法、可量化改善 |

每案最少回答四題：
- [ ] **為什麼做？** 主要使用者、關係人、原始痛點。
- [ ] **誰完成？** 自主使用或開發了哪些工具？哪些由資訊單位／委外負責？
- [ ] **怎麼驗證？** 成品、試用、測試題、樣本、驗收方法。
- [ ] **改善多少？** 基準值與導入後數值（工時、成本、錯誤率、筆數）、受益單位數、計算口徑。
- [ ] RAG／問答類：標準題、來源核對、正確率／符合度、無答案辨識；門檻依應用風險訂，不套固定數字。
- [ ] 措辭：「無法判斷／不表示加分意見」與「反對」是否分清？最終評核權是否留給 KPI 權責單位？

## D. 教育訓練、人才培育
- [ ] 目的：是要讓學員立刻精通，還是建立「知道有什麼」的腦中索引與拆題能力？
- [ ] 學員是誰？基礎差異？課後希望帶走什麼（「原來也可以這樣做」）？
- [ ] 教材是否從需求剖析 → 元件認識 → 迭代版本 → 實際業務場景 → 部署分享，涵蓋完整歷程？
- [ ] 主辦權責：全組織訓練由人資主責，資訊單位提供專業與必要課程？分工與預算是否依最新資訊？
- [ ] 量化比較：各單位課程總額、堂數、時數、每堂單價、內容規格；分母是否正確；內部講師／助教的人力成本是否計入？
- [ ] 是否考慮外部專家承擔規劃與授課，資訊單位保留專業把關？
- [ ] 報價項目是否界定必要服務與可驗收成果？
- [ ] 成效：課後如何檢驗學員能獨立拆解實際問題？
- [ ] 這其實是「PoC 試用收集回饋」還是「正式教育訓練」？不要用場次取代驗證成果。

## E. 跨單位分工、權責協調
- [ ] 這件事的權責主體是誰？資訊單位是陪跑還是攬責？
- [ ] 業務單位是否親自參與拆題、決定 SOP、欄位、KPI、行動計畫？是否有具協調／決策能力的主管在場？
- [ ] 建議是否只給方法、架構與一個小題示範，而不是替對方寫完整企劃？
- [ ] 是否有替其他單位「創設規則」的情況？跨單位定義不一致處是否先形成共識？
- [ ] 協助範圍：基礎設施、資安、技術整合、資料標準——這些要積極協作。
- [ ] 是否回溯原始往來紀錄，確認當初分工的表述？
- [ ] 溝通前是否整理：要談的問題、關係人、所需佐證、可能質疑與擬答？

## F. 執行計畫、進度回報、列管
- [ ] **Why／What／When／Value**：每項任務能否說出為何做、做到什麼程度、何時完成、做完解決什麼？
- [ ] 任務是否拆到可驗證、可估時？只寫「評估、協調、導入、優化、測試」的項目，交付與驗收是什麼？
- [ ] 是否把分工表、進度百分比本身當成目的？
- [ ] 全貌：數量、對象、類型、時程、先後次序、驗收條件。
- [ ] 日期：預定目標日與最晚驗收日是否分開？是否誤寫成已完成？
- [ ] 使用者便利：是否替使用者（尤其長官）減少額外手續？跨單位資源是否整合？
- [ ] 資料規範：表格狀態與欄位定義是否跨人可讀、一致？有沒有列未採購的服務造成誤會？
- [ ] 回報：短摘要包含 目標與數量／已完成與剩餘／下一步與日期／障礙與需協調事項／預計驗收日，並附詳表連結？
- [ ] 是否主動回報，讓主管不必追問？
- [ ] 是否有後續知識累積（做完的經驗寫下來可傳承）？

## G. 單純決策提問
1. 先用一句話重述目的與要解決的問題。
2. 分辨眼前必交付 vs 中長期工作，與時間限制。
3. 給出熊主管的判斷方向與理由，附類似案例或原則對照。
4. 區分：技術可行、業務可用、組織可落實。
5. 提出可立即採取的下一步、待驗證假設、留給使用者自己想的部分。

## H. 採購評選（評選委員角度）
- [ ] 本案處在哪個階段？要買的是可行性、規劃設計、建置能力，還是既有問題改善？
- [ ] **規劃設計案（PoC 後）**：廠商有沒有事前做功課（現場用途、機具、動線、流程、風險）？能否區分已知與待場勘事項？能否估算設備、費用、期程與後續關鍵路徑？成果能否變成技術中立、可招標、可驗收的規格與指標？
- [ ] **擴充／改善案**：既有痛點是否被具體處理？交付責任與交期風險怎麼控管？跨單位資料能否真正共享與更新？停機、移轉、備份復原如何驗證？
- [ ] 提問是否回到公告評選項目與配分，而不是臨時創設門檻？
- [ ] 希望納入履約管理的事項，哪些屬原契約既有義務（可釐清驗證方式）、哪些是契約外新義務（須循正式程序）？
- [ ] 不以投標價格高低或單一投標就預設結果。

## I. 高影響管控措施推動（資安、權限、白名單）
- [ ] 目的是什麼？要降低哪種風險、避免哪種業務中斷？
- [ ] 一次全面強制，還是先告警／稽核試行？產品是否支援？
- [ ] 是否收集真實事件樣態，區分版本更新、重複下載、合法業務需求與真正可疑？
- [ ] 識別依據是否只靠檔名或單一雜湊？有沒有結合簽章、版本、發行者、可信來源？
- [ ] 例外申請、申訴與支援流程是否先設計？轉入強制的條件與時程？
- [ ] 能否用可信資料批次匯入、自動化減少人工？是否仍保留風險審查與人工覆核？
- [ ] 成效指標是否包含誤判、工時、使用者干擾與資安成果，而不只完成筆數？
- [ ] 已確認惡意或高風險的事件，是否仍立即處置？

## J. 研究報告、效益估算、政策分析
- [ ] 這份研究要支援哪一項具體決策（投資、招商、補助、政策）？
- [ ] 每個數字的證據等級：實測、替代係數、外國參數，還是示範假設？是否標示待校準？
- [ ] 是否混用交易額、產出、增加值、地方所得、公司營收與公司淨效益？
- [ ] 國家、地方、公司各自的受益與成本是否分開？是否扣除替代消費與境外漏損？
- [ ] 策略比較是否固定其他條件、建立反事實？交易差異能否當作政策因果？
- [ ] 異常數字是否追查到計算鏈（情境、用量、天數、比例）？不預設算錯，也不預設正確。
- [ ] **Risk**：這份說法若被長官或政府照單全收，最可能造成什麼錯誤決策？
- [ ] 審閱重點放在資料解讀，而不是模型介面或網站功能。

## K. 共享平台／AI 服務營運與資源治理
- [ ] 推廣後多人同時使用，最可能先發生什麼服務問題（中斷、延遲、互搶資源）？誰會抱怨？
- [ ] 角色是否區分（唯讀查詢／編輯／高資源操作）？重度作業（如微調）是否集中排程？
- [ ] 平台團隊、基礎設施單位、廠商的分工是否寫清？
- [ ] 量化或模型選擇是否實測品質、延遲、併發、記憶體，而不是假設可一鍵切換？
- [ ] 資源切分與資料／模型權限隔離是否分開設計？
- [ ] 是否提出替選方案與效益驗證，而不只陳述硬體限制？
- [ ] 正式資源到位前，管理制度與基礎設施規劃如何銜接？

## L. 競賽、請益會議、多輪審閱的交版節奏
- [ ] 今天交的是正式投件、供諮詢的初版，還是後續優化版？品質門檻不要混用。
- [ ] 近期是否有已知的外部回饋節點？若有，先交基準版本，回饋後集中修訂。
- [ ] 審閱意見與「此階段必須執行」是否分開？A／B 分級不自動等於當日派工。
- [ ] 意見篩選是否依「評分影響 × 可行性 × 時間成本 × 證據成熟度」？
- [ ] 專家建議是否分立即採納／擇要採納／後續參考？當場是否避免承諾大量新工作？
- [ ] 角色定位：是幫主辦單位聚焦取分，還是不自覺在挑戰或重做對方的成果？
- [ ] 敘事是否連貫（痛點 → 解法 → 實證 → 管理價值 → 可擴散），而不是堆技術名詞？
- [ ] 指標口徑（定義、期間、算法、重算或再測）是否透明？有沒有一件完整真實案例？
- [ ] 必要底線：明顯數據錯誤、資格缺漏、資安或資訊揭露風險，是否優先處理？
- [ ] 是否具體肯定同仁投入，又不把熬夜當成績效標準？
