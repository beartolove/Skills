# 核心原則（審閱時的判斷依據）

資料來源：主管 2026/10/19–10/28 對談整理。標籤見 SKILL.md。

## 一、目的先行，每步回頭檢查（P1）
- 【主管確認】每件事先交代目的、做法與底層邏輯；以能否論證、說服為準，不以職位決定對錯。
- 【主管確認】辨識主要 User 與其他關係人，問清「真正的痛點」，把問題拆解成步驟，並在每一步 review 是否仍符合目的。
- 【主管確認】**減法常比加法重要**：新增需求／功能都要追問是否必要、是否解決核心痛點。
- 審閱追問：目的一句話是什麼？誰是使用者？這個功能刪掉會怎樣？

## 二、時效與階段性交付（P2）
- 【主管確認】先看目前有多少時間、必須交什麼；不要為追求八九十分而錯失時點。
- 【主管確認】歡迎中長期規劃，但要區分「眼前要完成的」與「階段性成果」，不能以遙遠願景取代近期交付。
- 【待確認】時效與法遵／資安／安全底線衝突時的處理，主管尚未定論；不可自行解讀為可犧牲底線。
- 審閱追問：這週／這個月實際交什麼？第一階段成果是什麼、如何驗收？

## 三、規範映射與一致性（P3）
- 【主管確認】相似目的的事應可對照一致的規範或處理邏輯；成本與現場彈性要考慮，但不過度干涉主軸。
- 審閱追問：類似案件過去怎麼處理？本案哪裡不同、為何要例外？能否對照？
- 多據點一致 ≠ 所有據點同一套系統：總公司訂業務規範、資料交換、驗證標準與管理追蹤；各據點依特性在地落地。【主管確認】

## 四、業務所有權：協助不等於接管（P4）
- 【主管確認】管理措施、KPI、SOP、長期藍圖、Action Plan，原則上由有業務權責的主管與同仁自行構思、執行與驗證；資訊處提供拆題方法、資料標準、工具、技術可行性與小範圍示範。
- 【主管確認】OT 等現場系統由所屬業務單位承擔管理責任，資訊處提供技術／資安協助，不無限制接管。
- 【主管確認】業務目的、流程、資料來源、規則、驗收條件，須由業務主辦單位先統整並與關係單位取得共識，資訊處再轉為系統或訓練方案。
- 例外：跨單位共用基礎設施、技術風險、資安、系統整合仍需資訊處積極協作——「不代做」不是「不協助」。
- 審閱追問：這份文件是誰的責任？資訊處是否把整份企劃都寫了？業務單位有沒有參與拆題？

## 五、先管理、先分類、再制度、最後才技術（P5）
- 【主管確認】先釐清方向 → 權責 → 資源排序；不要從單一系統需求直接跳到採購或開發。
- 【主管確認】先按業務情境分類（例如人事異動不同生效機制），定制度與責任，再定資料語意與 API；複雜例外不必全部技術化，可由 SOP／人工流程處理。
- 【主管確認】現有 SOP、流程、表單、欄位、資料品質沒先講清楚，建系統也無法可靠分析；不是把紙本照搬成電子檔。
- 業務與技術討論可分場進行，避免過早陷入欄位細節。
- 審閱追問：誰負責？什麼流程？怎樣驗證？資料欄位定義一致嗎？有沒有低成本的小題可先驗證？

## 六、向上溝通：看決策者、結論先行（P6）
- 【主管確認】高階主管若誤解既有工作是片段、無整體規劃，要主動及時對齊；5–10 分鐘、結論先行，把分散項目包裝成完整管理主題（如安全管理）。
- 【主管確認】先理解決策者當下在挑戰什麼（成本／時間／風險／效益）。最高層長官正檢討成本時，不先談大額建置；有限時間先給三年藍圖與具體案例，不堆功能 Demo。
- 【AI推論】報告者位階與信任程度會影響被接受程度，溝通方式需調整。
- 【主管確認】要有行銷與品牌意識：結論先行、一句話摘要、一頁式圖卡；正式簽案可完整，但每個決策階段另備對應決策者的一頁小抄（目的、需決定事項、後續）。
- 不要用 AI／VLM 等名詞或 Demo 數量取代應用情境；先有清晰情境再談技術名詞。
- 局部試驗不要對外宣傳成全面能力，避免主管機關或民眾誤解。

## 七、證據與量化：事實、估算、假設分開（P7）
- 【主管確認】要求成本、替代方案（自建／委外／既有產品／雲端／地端／混合）、資料來源、預期效益；區分已確認事實、估算、假設。
- 【主管確認】事先預判長官、會計、人資、業務單位的質疑並備妥擬答與佐證；可用 AI 模擬不同角色提問。
- 【主管確認】所有 KPI／效益主張要有：基準值、改善後數值、計算口徑、驗證方法。AI／RAG 要有回答正確率、符合度、人工驗證。
- 避免錯誤比較：例如把「總預算 ÷ 人數」當成「每堂單價」；現金支出低不代表人力負擔低。
- 外部案例用來啟發，不可直接套作本公司成本依據。

## 八、執行要可列管、可交代（P8）
- 【主管確認】上呈先講全貌與決策重點；執行要有範圍、數量、對象、期程、先後、驗收條件；回報讓主管不必追問。
- 工作法：掌握全貌 → 拆解工作 → 規劃期程 → 換位思考／跨單位協調 → 統一資料 → 列管進度 → 主動摘要回報 → 驗收結案。
- 回報格式：**短摘要（LINE）＋可查詳表（Sheet）**。摘要含：目標與數量／已完成與剩餘／下一步與日期／需協調障礙／預計完成驗收日。Sheet 是可稽核細節，不是摘要的替代品。
- 表格狀態與欄位要跨人可讀、定義一致；不要列入尚未採購的服務造成誤會。
- 以使用者便利為先，優先善用既有資源，減少長官與現場人員的額外手續。
- 不以文件寫得漂亮代替真正執行；時間與承諾以承辦追蹤、主管核定與實際驗收為準。

## 九、人才培育與指導方式（P9）
- 【主管確認】希望同仁「帶問題與答案」來討論；現階段主管仍會親自示範（簡報／結論 sample），急件給部分方向、保留思考空間；非急迫則放手讓同仁嘗試。
- 【主管確認】業務現場導向：粗略 POC 就應盡早找業務單位問「與你想像的落差多少」，依回饋修正欄位、功能、介面，不閉門開發。
- 【主管確認】同仁認知落差常源於缺乏業務／現場經驗與溝通，也有制度與知識傳承缺口；不要只歸咎個人，也不要泛化為所有資訊人員。
- 【主管確認】培育不限儲備主管；安靜的同仁也可能有深入判斷。重視「有沒有動起來」——思考、回應、持續修正都算進步，不要求第一次完美。
- 【主管確認】教育訓練先建立「知道有什麼」的腦中索引，讓人能組合解題，不以立即精通語法為唯一成功條件。
- 同仁要從「單兵執行」成長為能協調、溝通、主動解題的工作者。

## 十、KPI／創新加分判準（P10，D 情境專用）
- 【主管確認】**自主應用**（業務單位自行用公司提供的 AI／資訊工具解決明確痛點、完成具體應用）：原則支持，不以技術難易為門檻；須有具體可量化成果。
- 【主管確認】**正式系統建置／精進**：須先與資訊處溝通目的、構想與分工；若要資訊處背書「資訊創新加分」，原則期待跨單位效益與新作為（「至少二單位受益」為主管針對此類的判斷原則，不套用到所有自主工具）。
- 【主管確認】屬原有職掌的單位內系統開發／維運／例行精進：資訊處不表示加分意見，由提案者向 KPI 評核權責單位自行說明；**不等於反對**。最終加分決定不由資訊處代行。
- 【主管確認】AI、系統、智慧化等字樣本身不是加分理由；需求不明（痛點、產出未定義）→ 請補述。
- 四個必答題：為什麼做？誰完成？怎麼驗證？改善多少？

## 十一、預算與資源排序（P11）
- 【主管確認】排序示範：資訊處必要與已執行項目優先保留 → 其他單位依案評估減量／分年／先單點驗證再擴散 → 之後才考慮增額。資源排序是為了整體可行，不是全面否決需求。
- 新舊系統持續增加時，長官與會計關切效益與資安成本；資安經費比例等規範的適用範圍須先核對，不可直接引用。
